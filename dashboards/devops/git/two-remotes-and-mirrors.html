One repo, two homes

The Learning Lab lives on GitLab, which runs its website, and has a copy on GitHub. This page shows how a project keeps two homes in step, the two ways to do it, and why splitting topics into separate repos still leaves one website.

Key idea: one home is the main copy and the other is a copy of it. The only question is who carries each change across: your computer, every time it pushes, or GitLab, every time it receives anything.

1. What a remote is

Your computer holds the project. A remote is a saved name for another copy somewhere else, plus where to fetch from and where to push to.

Analogy: you keep a notebook at home. GitLab is the library that holds the official copy and shows it to the public. GitHub is a friend's house holding a photocopy. A remote is an entry in your address book: "origin: the library". One address-book entry can list two places to deliver to.

The Lab's real settings

From git remote -v in the project folder

origin  gitlab.com/Prabidhi/…  (fetch)
origin  gitlab.com/Prabidhi/…  (push)
origin  github.com/Prabidhi/…  (push)

One fetch line: downloads come only from GitLab. Two push lines: every git push goes to both. Set with:

git remote set-url --add --push \
    origin <gitlab address>
git remote set-url --add --push \
    origin <github address>

The first command matters: once you add any push address, git stops using the fetch address for pushing, so GitLab has to be listed again.

    3. What each way needs

    Creating the GitHub repo is the same in both. The difference is who carries changes across, and whether that someone needs a key.

    Push to both from this MacGitLab mirrors to GitHub
    Who copiesYour computer, during each pushGitLab, a few minutes after anything reaches it
    Setup on GitHubAn empty repoAn empty repo, plus a token with permission to write to it
    Setup on GitLabNothingSettings → Repository → Mirroring repositories: GitHub address, direction Push, the token as the password
    Setup on the computerTwo push addresses on originNothing
    Covers website edits and other computersNo, until this Mac next pulls and pushesYes
    Ongoing careNoneMake a new token when the old one expires
    Why only the mirror needs a token: your computer already has its own keys to both houses, because you signed in to both. A mirror means GitLab walks to GitHub's house by itself, so it needs a key of its own. The token is that key, and only the account owner can cut it.

    4. Many repos, one site

    The plan is to give big topics, starting with Oracle, their own repo. Compare that with giving each topic its own website.

      Why the address matters: a browser keeps each website's saved settings in a separate locked drawer, one per address, and lets a page reach into another page only if both share the drawer. One address means one drawer for every topic.

      5. Where the copy lives

      Any Git host can be the second home. The Lab's rules prefer open-source services, so it's worth knowing the choice.

      GitHub

      Used for the Lab today

      Free for public repos, and where most people look for code. The service itself is not open source, so under the Lab's rules it is flagged, with an open alternative named.

      Codeberg

      The open alternative

      Free, run by a non-profit, and built on Forgejo, which is open source. It can receive pushes or a GitLab mirror in exactly the same way.

      GitLab

      The main copy

      Its core is open source, and it runs the pipeline and the website. Whatever the second home is, this one stays the source of truth.
