rules:
Decides which jobs are created. Your pages job only runs for main.
Analogy: the recipe card must be in the right slot with the right name, or the head chef never sees it. Even then, nothing is cooked until an order comes in, and the card can say "only cook this for the main dining room," which is what rules: does.

The runner is always on; the workstation is not

The runner service keeps asking GitLab "any jobs for me?" A container exists only while a job runs.

Executor:
gitlab-runner servicepolling: 0 checks
Job workspacejobs waiting: 0
No job is running, so there's no container.
Analogy: the line cook stays in the kitchen all shift, checking the order rail every few seconds. When a ticket shows up, they set up a clean station, cook, hand off the tray and clear the station. Nobody has to wake the cook up.

Which image will my job use?

Change the settings to see which image wins. The image provides the shell and tools (mkdir, cp) that your script needs.


      

    

    
Order of precedence: the job's own image, then the file's default: image, then the runner admin's default. The top-level default applies only to jobs in this one file and project. The runner default is the only setting that reaches across projects.

  


  

    
Why not just run on the runner machine itself? Tap each reason.

    

      
No leftovers
Each job starts from a clean state, so files from earlier jobs can't leak in, and a pass or fail means the same thing every time.

      
No tool conflicts
One project needs Node 18 and another needs Node 22, or Java 11 versus Java 21. Each container brings its own.

      
Security
A job runs whatever a .gitlab-ci.yml says. A throwaway container limits what it can read or damage. FedRAMP/FISMA-style environments usually expect this.

      
Parallel jobs
Several jobs can run at once without stepping on each other.

      
Reproducible
"It ran in alpine:latest" is precise. "It ran on that one box with whatever was installed" isn't.

      
When shell is fine
A dedicated runner for one trusted project, or a job that needs something only that host has. You then have to keep that machine clean yourself.

    

  







  

    
Pipeline, stage, job

    

      
Job
One task with its own script:. One runner runs it in one container. It passes or fails on its own.

      
Stage
A group of jobs that run side by side. The next stage starts only if every job in this one passes.

      
Pipeline
All the jobs created by one trigger, such as one push. It has one overall status.

Job names are mostly up to you: validate-html, check-links, anything. Only pages has a special meaning: its public/ artifact becomes your site.

        
With only the pages job, a pipeline and a job look like the same thing. They separate once you add more jobs.

        
Analogy: a pipeline is a whole dinner order for one table. Each job is one dish. Appetizers (the test stage) come out together, and the main course (the deploy stage) comes out only after them. A taste-tester (validate-html) can stop a bad dish before it reaches the counter.

Order matters: fill the tray, then hand it over

    
1. script: creates public/ inside the container and copies your HTML into it. 2. artifacts: uploads that folder to GitLab. 3. GitLab stores it as the Pages deployment (on EBS or S3). 4. The container is thrown away, and only the uploaded artifact remains.

    
Analogy: the cook plates the food on a tray (the script), then passes the tray through the window (artifacts:). If the cook plates it but never passes it through, it gets thrown out when the station is cleared.

  







  

    
Each project only publishes itself

    
A .gitlab-ci.yml belongs to the project it's in. Push to one project and watch the other.

    

    
To bring project2's files into project1's site, project1's job must fetch them on purpose: clone project2 with the job token, add it as a submodule, or download its artifacts. Using include: from another project shares the pipeline configuration, not the other project's files.

    
Analogy: each project is its own restaurant, with its own recipe book, pantry and shop window. project1's cook only uses project1's pantry.

    The three ways to take a site down
    
    
    
      
    OptionWhereEffect
    
      
    Remove pagesDeploy → Pages → Remove pagesDeletes the deployment. The URL returns 404 until a pages job runs again.
    
      
    Turn off without deletingSettings → General → Visibility, project features, permissions → PagesStops serving the site. Turn it back on later and the same site returns.
    
      
    API, for scriptsDELETE /api/v4/projects/:id/pagesSame as Remove pages.
    
    
    
    
    Deleting the whole project also removes its site. The main Pages deployment doesn't expire by itself. The job's own artifact copy may expire under your instance's retention policy, but that doesn't affect the live site.
    
    
    Analogy: deleting .gitlab-ci.yml cancels future deliveries. The last stock stays on the shelf, and the clerk keeps selling it. To empty the shelf, you have to clear it yourself with Remove pages.
