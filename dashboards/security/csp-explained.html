CSP, explained: the rule that keeps these pages offline

Every dashboard on this site carries a Content Security Policy. This page shows what it does, using your browser's real behaviour, and why one small tag needs a script and a pipeline check to stay correct.

Key idea: the meta tag does the protecting, but it stops matching when a script changes. It lists the exact fingerprint of each script. Change a script and its fingerprint changes, so the browser refuses to run it. There's no expiry date: an unedited page keeps working indefinitely. update_csp.py keeps the list correct, and the pipeline check catches you if you forget.

1 · Three ideas that get mixed up

Standalone, offline and CSP sound like one thing, but they answer different questions.

Think of a club door. Your page is the club and the browser is the bouncer. The CSP is the guest list you hand over at the start of the night. If a name isn't on the list, it doesn't get in, no matter how it arrived.

Standalone

Where does the code live?

All the CSS and JS sit inside one HTML file. Nothing needs to load from a separate file.

Who guarantees it? You, by how you write the page.

Offline

Does it need a network to run?

Once the page is open, it makes no network calls. You still need a connection to open the hosted site, or a copy on your computer.

Who guarantees it? You, unless something enforces it.

CSP

What is the page allowed to do?

A list of rules the browser enforces while the page runs. It blocks anything the list doesn't allow.

Who guarantees it? The browser, on every page load.
Without a CSP, "offline" is a good habit. With a CSP, it's a rule. If a future edit, or injected code, tried to call a server, the browser would stop it.

Three rules worth remembering

Put it first. The tag must come before the first script, or that script runs before any rule exists. That's why it sits straight after <meta charset>.

Hashes switch off 'unsafe-inline'. If a directive lists both, browsers ignore 'unsafe-inline'. So your pages use one or the other for styles, never both.

A meta tag has limits. frame-ancestors, which stops other sites embedding a page, only works as a server header, so it can't be set here.

4 · Hashes: a fingerprint for code

A hash turns any text into a short fixed-length code. The same text always gives the same code, and the tiniest change gives a completely different one. This is real SHA-256, the same calculation your browser and the Python script both do.

The guest list holds fingerprints, not names. A name could be forged, but a script can't fake its fingerprint. That is what lets the policy say "only this exact code".

5 · So why isn't the meta tag enough?

The tag is enough on the day you write it. The trouble starts on the next edit. Adding a dashboard edits the script inside index.html, so the tag now holds an old fingerprint.

Easy to mix up: GitLab does not recalculate your hashes. update_csp.py runs on your computer and rewrites the files before you commit. GitLab only runs update_csp.py --check, which reads the files and passes or fails. It never edits them.

Your computer

Runs update_csp.py

Recalculates hashes and writes them into the HTML files. You commit the result, so your repository always holds the correct tag.

GitLab

Runs update_csp.py --check

Recalculates hashes only to compare them. If anything differs it fails the job, which stops the pages job from deploying.

Could GitLab fix the hashes itself? Yes, a pipeline could rewrite them at deploy time. We chose not to, because the live files would then differ from your repository, and a copy opened from your computer would still carry stale hashes. Checking keeps one source of truth.

7 · What we did on this site

  
The steps, and why each one was needed.

  

    

      
Audited all 9 pagesAll were standalone and made no network calls, but only the GitLab page had a CSP.

      
Found a real bugThe home page adds a small style rule to hide each dashboard's theme switch. The GitLab page's strict policy blocked it, so that page showed two switches. Its hash had to be added.

      
Chose a policy for the other 8Scripts are locked to hashes. Styles use 'unsafe-inline' because six pages use style="..." attributes, and so editing CSS can't break a page.

      
Opened one door on the home pageframe-src 'self' lets it load dashboards from the same site. Without it, no dashboard could open.

      
Added the script and the checkupdate_csp.py keeps hashes current, and csp-check blocks a stale deploy.

      
Tested it by breaking itA deliberately blocked copy proved errors would be caught. A changed list and a page with no policy both failed the check.

    

    

      
Your routine from now on
After editing a page or adding a dashboard:


python3 scripts/update_csp.py
git add -A
git commit -m "Add a new dashboard"
git push

        
Editing only the text or CSS of a page doesn't change any script, so its hash stays the same. Running the script anyway is harmless.

      
What this does not cover

        
Inline styles are still allowed, though with images, fonts and network calls blocked they can't send anything out.

        
Other sites embedding your pages needs frame-ancestors, which a meta tag can't set.

        
Links people click aren't blocked, which is why the Korean page's translate links still work.

        
Separate files like an image next to a page are blocked too. A page that needs one needs its policy edited by hand.
