APEX: Daily API Loads and Email

What it takes to call an outside API from Oracle APEX every day, keep the rows in a staging table, and email when it's done.

Key idea: you can write all the code yourself, but three things usually belong to someone else: the gate to the internet (a network rule), the timer (the CREATE JOB privilege) and the post office (a mail server).
Built from a hands-on lab on a laptop: Oracle Database 23ai Free, APEX 24.1, ORDS 25.3. The API was JSONPlaceholder, a public fake-data test API. Results marked tested were seen in that lab; not checked means expected but not tried there. Names are generic.

2. The gate: why an API call can fail before it leaves

When an APEX page or job calls an API, the database makes the call, not your browser. Before any data leaves, Oracle checks its network access list: "may this account connect to this host on this port?" Only a DBA can add entries.

Analogy: the building's security desk keeps a guest list of outside addresses. If the address isn't on the list, your courier is stopped in the lobby, however good the parcel is.

    What the error looks like tested

    APEX shows the top line. The real reason is further down the stack:

    ORA-29273: HTTP request failed
  ...
ORA-24247: network access denied by
           access control list (ACL)

    If you see ORA-29273, look for ORA-24247 underneath. That means: ask the DBA for a network rule for that host and port.

    The rule names the account that makes the call. With apex_web_service or a REST Data Source that's APEX's own schema (for example APEX_240100), not yours.

    Older databases (such as 19c) also need a wallet: a file of trusted certificates for HTTPS. The 23ai lab didn't need one, because it trusts the operating system's certificates. not checked on 19c.

    3. Privileges, one at a time

    In the lab, the app's schema had every privilege removed, and each one was added back only when an error proved it was needed. Switch them on and off to see what each one unlocks. Every result below was tested.

    Analogy: privileges are keys on a key ring. Owning a room (your tables) needs no key; you can always go in. Keys are for making new things: a new room, a new machine, a new calendar slot.
    Presets:

      Direct grant or role? It matters.

      Look at two views: USER_SYS_PRIVS lists privileges granted to you directly; SESSION_PRIVS also includes those that come through roles (such as Oracle's standard RESOURCE role).

      Oracle switches roles off inside stored PL/SQL, and APEX runs your code without them. So privileges you only have through a role can work in SQL Developer and still fail inside APEX or your own procedures. Ask for what APEX needs as a direct grant. not checked in the lab for APEX; the PL/SQL rule is standard Oracle behaviour.

      The silent failure tested

      1. A scheduled REST synchronization ran while the schema had no CREATE JOB.
      2. Oracle's scheduler log said SUCCEEDED.
      3. APEX's own sync log said Failure: ORA-01031 insufficient privileges, 0 rows.
      4. APEX then quietly switched the sync off ("Job is Active" unticked), so nothing ran at the next tick.

      Lesson: check APEX's own logs (APEX_REST_SOURCE_SYNC_LOG, APEX_AUTOMATION_LOG), not just the scheduler's.

      5. Inside an APEX automation

      An automation is APEX's built-in "do this on a schedule, or when asked". Its edit page has a few sections. Open one at a time.

      Name

      Name is a label for people. Static ID is a fixed code name that code uses, for example apex_automation.execute(p_static_id => 'refresh-todos'). Renaming doesn't change the Static ID. Currently Executing says Yes while a run is in progress; APEX won't start a second one on top.

      Settings: when it runs

      Type: Scheduled (APEX's timer runs it) or On Demand (only the play button, a page button or code start it).

      Schedule Expression: the timetable as a short code. Every night at 2 am is FREQ=DAILY;BYHOUR=2;BYMINUTE=0. The wrench icon builds it for you.

      Schedule Status: Active (timer on), Disabled (off). Switching to Active failed with ORA-01031 without CREATE JOB. tested

      Actions Initiated On: run the actions Always, or base it on a Query, or on a yes/no function. Try it below.

      Source: what rows to look at (only with Query)

      A table or SQL query in your schema, a remote database, or a REST Data Source. With "Rows returned", each row's columns can be used in the actions, for example :INVOICE_NO.

      Actions: the actual work

      Each action has a Name, an Execution Sequence (10 runs before 20), a Type (Execute Code, Send E-Mail, Send Push Notification) and a Location (this database or a remote one).

      A good habit: keep the real logic in your own procedure and make the action just call it, for example begin todos_refresh; end;. Then the same code runs from the automation, a button or a DBA's job.

      Stop Execution On Error: if action 10 (the load) fails, action 20 (the "load finished" email) is skipped.

      Action Execution: what happens on errors

      Commit once at the end, or after each row. Maximum Rows to Process is a safety cap. Action Error Handling: Ignore (log and carry on), Terminate (stop this run) or Disable (stop and switch the schedule off until someone fixes it).

      Additional Code Execution

      A small block of PL/SQL for helper procedures, plus three hooks: run something once at the start (for example read the last successful load time), before each row, and once at the end (for example write a load log row). Many teams just call a package here, such as begin load_pkg.init; end;.

      Try it: how many times do the actions run?

      6. Email: APEX writes it, a mail server delivers it

      APEX's Send E-Mail action (and Oracle's APEX_MAIL, UTL_MAIL, UTL_SMTP) only write the email and hand it over. A mail server does the delivery. Pick a post office and step through.

      Analogy: writing an address on an envelope doesn't deliver it. You hand it to a post office, which carries it to the right house. Some post offices want to know who you are first, and that's your own account, never the recipient's.

        Questions people ask

        "I have the email address. Why isn't that enough?"
        The address says where the email goes, not how it gets there. In the lab, sending straight to Gmail's own mail server on port 25 was blocked by the internet provider, which is common to stop spam. tested

        "Why would Gmail need a password? I'm not logging in as the person I'm emailing."
        Right. The password is the sender's: APEX signs in to a Gmail account it sends from, like you sign in to Gmail before writing to anyone. The recipient's password is never involved.

        "Does Oracle have its own mail server?"
        Not inside the database. Oracle's cloud has an email delivery service, but that's another account to set up. At work, the company's mail server is usually set in APEX once by an admin.

        "When does a queued email go out?"
        APEX's background job sends queued email every 5 minutes. apex_mail.push_queue sends straight away, but only inside an APEX session. tested
