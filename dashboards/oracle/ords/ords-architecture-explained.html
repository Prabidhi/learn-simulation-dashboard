ORDS Architecture, Explained

What sits between an HTTP request and your PL/SQL: an application server such as Tomcat, the ords.war web app, the JDBC driver, a pool of open database connections, and one database account that acts on behalf of your REST schema.

Key idea: ORDS never logs in with your schema's password. Its pooled connections log in once as ORDS_PUBLIC_USER, then act as your REST schema for each request. From there, your schema's grants decide everything it can reach, including objects in other schemas.

Colours follow who is acting: nobody yet ORDS itself ORDS_PUBLIC_USER WS, your schema APP's rights OTHER.V

The simulations are simplified. Each fact is labelled: checked in a lab (ORDS 25.3.1 with Oracle AI Database 26ai Free), read from ORDS's code, or reasoned from those tests.

2The office analogy, checked

      
Each note is one step of a common way to picture ORDS. Decide whether it's right, then compare.

    

    

    

    
The analogy, corrected: Tomcat is the building and ORDS an office in it. A clerk reads the request slip to find the database, the flat (schema) and the service, and the security desk checks the visitor's pass. The office keeps phone lines already connected to the database building, each answered with the ORDS_PUBLIC_USER badge. For each request a line is lent out and switched to act for the flat on the slip. Inside, the flat uses only its own permissions: it calls a neighbour's service through a hatch it's allowed to use, and the neighbour's staff do that work with the neighbour's keys.

  


  

    

      
3Reaching other schemas

      
ORDS never logs in as a second schema. Your schema reaches objects in other schemas only through grants. The handler calls app.p.get_count, and package P reads OTHER.V. Switch the grants and watch the chain.

    

    

      
      
      
    

    

    

      
 

      
      

      
    

    
Analogy: the courier stays in the WS flat. It passes the request through the neighbour's service hatch, which takes WS's permission (EXECUTE). The neighbour's own staff fetch from the storeroom with the neighbour's key (APP's grant) and hand the result back through the hatch.

    
P uses definer's rights, the default, so its code runs with its owner's rights. A package can instead be declared to run with the caller's rights (AUTHID CURRENT_USER). The lab didn't test that case, so it isn't simulated here.

  


  

    

      
4The connection pool: new and warm lines

      
On ORDS 25.3 with a 12c or newer database, the driver asks SYS.DBMS_PICKLER for the layout of OWA.VC_ARR before a line runs its first PL/SQL handler for a schema, then remembers the answer. Send requests, let time pass, take grants away and restart ORDS.

    

    

      
      
      
      
    

    

      
      
    

    

    

    
    
    
    
      
    New line
    It has never asked for this schema, because it was just opened or just switched from another schema. The driver asks DBMS_PICKLER, running as the schema.
    
      
    Warm line
    It already asked for this schema and kept the answer, so it doesn't ask again. A grant removed later stays hidden until the line is replaced.
    
      
    Not in the database
    New and warm live in ORDS's memory, per line and per schema. The grant lives in the database. A brand-new schema always starts on new lines.
    
    
    
    
    Simplified: ORDS's pool library (UCP) has its own way of choosing lines. The rules shown match the lab: one lookup per line per schema, idle lines stay open, and a used line older than 60 seconds is replaced (jdbc.MaxConnectionReuseTime, 60 seconds by default in 25.3). That a line switched to another schema forgets the first schema's answer was read from the driver's code; the lab had only one REST schema.
