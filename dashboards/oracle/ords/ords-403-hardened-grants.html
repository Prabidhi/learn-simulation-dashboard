ORDS troubleshooting · lab tests from 7 Nov 2026

Why every PL/SQL handler returned 403

In a real case, even a one-line handler like BEGIN :status_code := 200; END; failed with 403, while plain SQL GETs kept working. ORDS runs extra PL/SQL as your schema around every PL/SQL handler, and that code needs packages a hardened database took away from PUBLIC. A lab rebuilt it to find which ones, and found that open connections can briefly hide one of them.

Cause

Hardening removed two packages from PUBLIC. SYS.DBMS_LOB is needed after every handler, on every request. On ORDS 25.3, SYS.DBMS_PICKLER is needed before the handler, once per new connection. Connections that already used it remember the answer, but ORDS keeps replacing connections as they're used, so a missing grant only stays hidden briefly.

Fix

A DBA grants EXECUTE on both SYS.DBMS_LOB and SYS.DBMS_PICKLER to each REST schema whose PL/SQL handlers fail. PUBLIC can stay revoked, and both grants are low-risk (section 7).

Ruled out

Tomcat vs standalone, whole module vs URL pattern, roles (they give 401), and HTP or OWA (still granted to PUBLIC).

3. Read the status code

The code alone tells you which half of ORDS stopped the request.

401

Security stopped it

No token, or the token's client lacks the privilege's role. A missing role is still 401. We also saw it when ORDS's own sign-in code could not use OWA.

403

PL/SQL could not compile

Security passed. One of the PL/SQL statements ORDS runs as your schema names something the schema cannot see (PLS-00201). “The PL/SQL statement being evaluated” can be ORDS’s own setup or after-code, not only your handler. ORDS’s log shows which one, with line numbers.

555

Found, but it failed

The schema can see the object, but it fails when run, for example an INVALID package body (ORA-04063).

4. Check your database

Run these logged in as the schema the failing URL belongs to. They only read.

Compare grants

Run it as a working schema and as the failing one. What the working one has and the failing one lacks is the likely cause of today's 403. If neither has DBMS_PICKLER, the two probes below show why the working one still works.

select table_name, grantee, privilege
from   all_tab_privs
where  table_schema = 'SYS'
and    table_name in ('DBMS_LOB','DBMS_PICKLER','DBMS_UTILITY','OWA','HTP','WPG_DOCLOAD')
and    privilege = 'EXECUTE'
order  by table_name;

Confirm the handler types

A working schema proves something only if its handlers are plsql/block. Plain SQL handlers never use these packages.

select m.uri_prefix || t.uri_template as url_after_schema,
       h.method, h.source_type, m.name as module
from   user_ords_handlers  h
join   user_ords_templates t on t.id = h.template_id
join   user_ords_modules   m on m.id = t.module_id
order  by 1, 2;

No DBA needed. Run it as the working schema. It always errors, on purpose: x is a made-up name, and nothing runs. PLS-00302 means the schema can use DBMS_PICKLER; PLS-00201 means it can't. If it can't and its plsql/block handlers work, your ORDS version doesn't need DBMS_PICKLER.

Which ORDS version?

No DBA needed. Run it in both schemas. The same version means the same ORDS behaviour.

select ords.installed_version from dual;

Who can use DBMS_PICKLER (DBA)

Needs a DBA view. If the working schema, or a role it has, isn't listed, its ORDS version probably doesn't call DBMS_PICKLER, or its handlers aren't PL/SQL. Warm connections can't explain it for long, because ORDS replaces connections as they're used (section 6).

select grantee, privilege
from   dba_tab_privs
where  owner = 'SYS'
and    table_name = 'DBMS_PICKLER'
order  by grantee;

Compile ORDS's after-code

Nothing runs, because the calls sit inside IF FALSE. A PLS-00201 names what is missing.

declare
  lines  htp.htbuf_arr;
  n      number;
  l_clob clob;
  l_doc  varchar2(1000);
begin
  if false then
    owa.get_page(lines, n);
    dbms_lob.createtemporary(l_clob, true);
    if wpg_docload.is_file_download then
      wpg_docload.get_download_file(l_doc);
    end if;
  end if;
end;

5. Ask your DBA

Replace <SCHEMA> with the failing REST schema. It asks for both packages, so it works whichever way your ORDS version sends request data. Section 7 covers the risk of each grant.

Message to send

Only SYS, or a DBA allowed to grant on SYS objects, can run the grants.

Our ORDS REST schema <SCHEMA> returns HTTP 403 ("a function or procedure
referenced by the PL/SQL statement being evaluated is not accessible or does
not exist") on every PL/SQL handler, even BEGIN :status_code := 200; END;.

ORDS runs some of its own PL/SQL as that schema around each handler. That code
calls SYS.DBMS_LOB on every request, and its database driver calls
SYS.DBMS_PICKLER once per new connection. Both are revoked from PUBLIC on our
database. In a test environment, removing either one gave this exact 403, and
granting both to the schema fixed it. PUBLIC can stay revoked.

Our ORDS version may not need SYS.DBMS_PICKLER, but the grant is low-risk:
the driver only uses it to look up a type's layout.

Please run as SYS:

grant execute on sys.dbms_lob     to <SCHEMA>;
grant execute on sys.dbms_pickler to <SCHEMA>;

If the 403 continues right after, restarting ORDS (Tomcat) once gives it
fresh connections.

6. Inside the packages

Seven SYS packages sit around a PL/SQL handler. Pick one to see what it does, where ORDS calls it, whose rights it runs with, and where its grant came from. The facts come from the lab database and from reading ORDS 25.3's code.

Does ORDS need DBMS_PICKLER?

ORDS sends the request headers to the database as arrays. ORDS 25.3's code picks how by the database's major version.

How long a connection remembers

The database driver keeps DBMS_PICKLER's answer for as long as a connection keeps its session for your schema. Pick when DBMS_PICKLER was removed from PUBLIC.

    Timings are illustrative; the behaviour was tested in the lab. 119 PL/SQL calls needed only 11 lookups. Idle connections still remembered the answer after 40 minutes, but each was replaced right after its next use (ORDS 25.3 sets jdbc.MaxConnectionReuseTime to 60 seconds by default), and the replacement asked DBMS_PICKLER again.

    Analogy: DBMS_PICKLER is like asking for a parts list before packing a box. The driver needs the layout of OWA.VC_ARR before it can pack the request headers into one. Once a connection has the list, it keeps it.

    7. How risky is each grant

    Hardening takes powerful packages away from PUBLIC, because every account gets PUBLIC's grants, including a stolen one. Granting a package back to the one schema that needs it keeps that protection.

    Can this schema read a file on the database server?

    How concerned to be

    • LowDBMS_LOB

      Reading server files also needs a directory grant, and BFILEs can never be written. Oracle documents that its operations run as the calling user, even though SYS owns it.

    • Low, but undocumentedDBMS_PICKLER

      It mostly hands out type layouts: structure, not data. It runs with SYS's rights and has one write function, UPDATE_THROUGH_REF, which Java programs use to update an object through a reference. No hardening standard we found lists it.

    • Guard this oneDirectory grants

      READ on a directory is what opens the files in it. Check what a schema can reach before granting DBMS_LOB.

    Analogy: DBMS_LOB is a records clerk who carries a master key but still checks your library card. It only fetches from archive rooms (directories) your card covers.

    What files could this schema reach?

    Run it as the REST schema. No rows means it can't read any server file, with or without DBMS_LOB.

    select directory_name
from   all_directories
order  by 1;

    Why HTP and OWA kept their grant

    • Oracle grants all seven to PUBLIC

      Out of the box: the five web packages in owacomm.sql, DBMS_LOB in dbmslob.sql, DBMS_PICKLER in prvtpckl.plb. Hardening removed two of them on purpose.

    • DBMS_LOB is on the CIS list

      The CIS Oracle 19c benchmark (item 5.1.1.2) says PUBLIC shouldn't run its "File System" packages: DBMS_ADVISOR, DBMS_LOB and UTL_FILE.

    • The web packages are left alone

      HTP, HTF and OWA only build pages in memory, and APEX and the PL/SQL web gateway break without them.

    • DBMS_PICKLER isn't on any list we found

      A stricter in-house list or a security scanner may have flagged it. Your DBA knows which.

    • ORDS itself kept working

      ORDS's installer grants DBMS_LOB directly to ORDS's own accounts, so its sign-in survived. The code around your handler runs as your schema, which relied on PUBLIC.

    Sources, checked 7 Nov 2026
    • Oracle Database 19c, DBMS_LOB reference: its security model, and BFILEs being read-only.
    • CIS Oracle 19c item 5.1.1.2, "File System" packages, from Tenable's copy of the v1.2.0 audit.
    • The lab: its database dictionary (DBA_PROCEDURES, DBA_DEPENDENCIES, DBA_TAB_PRIVS), Oracle's install scripts, and ORDS 25.3.1's code and install scripts.

    8. Ruled out

    • Tomcat vs standalone ORDS

      Both run the same ords.war. The 403 comes from the database.

    • Whole module vs URL pattern

      It only decides which URLs need a token. A pattern covers GET and POST alike.

    • Roles and privileges

      Problems there give 401. A valid token without the role is 401 too.

    • HTP, OWA, OWA_UTIL, WPG_DOCLOAD

      Still granted to PUBLIC in the real case.

    • CREATE PROCEDURE

      The REST schema works with only CREATE SESSION and CREATE SYNONYM.

    • Your handler's code

      A one-line block fails the same way, so the problem sits in the code ORDS adds.
