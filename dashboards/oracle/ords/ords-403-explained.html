ORDS 403, Explained

A REST gateway schema with only CREATE SESSION and CREATE SYNONYM got HTTP 403 on its plsql/block POST handlers, while json/collection GETs worked with the same token. This page rebuilds the lab investigation so you can run every request yourself, then shows what the real database turned out to be missing.

Updated 7 November 2026. In the lab, revoking SYS.HTP reproduced the 403 exactly, so this page first named HTP as the cause. The real database still had HTP. It was missing SYS.DBMS_LOB and SYS.DBMS_PICKLER instead. Read what the real database was missing and why DBMS_PICKLER isn't needed on every request.

The fixgrant execute on sys.dbms_lob to <gateway>, then sys.dbms_pickler if ORDS's log still names it
Does the gateway need CREATE PROCEDURE?No
Reproduced in the lab, but not the real causeEXECUTE on SYS.HTP revoked from PUBLIC
Key idea: ORDS wraps every plsql/block handler in its own PL/SQL, and that code runs as your schema. Before your code, it sets up the request with OWA and HTP, and on a new connection ORDS 25.3's JDBC driver first asks DBMS_PICKLER for a type's layout. After your code, OWA, DBMS_LOB and WPG_DOCLOAD collect the response. If the schema can't reach any one of them, you get the same 403, whichever package it is. GETs from a json/collection source use none of them, so they keep working.

1. The setup at a glance

Two layers: the path a request travels, and the chain of schemas inside the database that does the work. The gateway never touches the repository directly. A definer's-rights package in the middle does. Tap any part.

Analogy: the gateway is a receptionist who may only pass notes to one office. The office (a definer's-rights package) has its own keys to the archive. And every written reply goes through the building's mailroom, a row of machines the receptionist must be allowed to use: a printer (HTP), an envelope packer (DBMS_LOB) and a few more. Take away access to any one machine and every written reply fails, even though nothing else changed. The lab switched off the printer first. In the real building the printer worked, and the envelope packer (DBMS_LOB) and a form-layout lookup (DBMS_PICKLER) were off.

    4. What it proved
    
  
    
    
    
      
    Four suspects
    
      
    HypothesisVerdictEvidence
    
        
    The gateway needs CREATE PROCEDURENoPhase 1 POST handlers returned 201 with only CREATE SESSION and CREATE SYNONYM
    
        
    The OAuth or privilege setup is the causeNoPhase 2: 401 without a token, 201 with a valid one
    
        
    Database hardening on SYS.HTPLab onlyRevoking it from PUBLIC reproduced the 403 on POST while GET stayed 200, but the real database still had HTP
    
        
    Database hardening on SYS.DBMS_LOB and SYS.DBMS_PICKLERYesThe real schema couldn't reach either. Revoking both in the lab gave the exact message, and granting both fixed it (section 5)
    
      
    
      
    Why GET and POST differ: json/collection GETs go through ORDS's own SQL path and never touch the wrapper packages. Every plsql/block handler runs inside ORDS's generated PL/SQL, which needs OWA, HTP, DBMS_LOB and WPG_DOCLOAD, plus DBMS_PICKLER on new connections.
    
    
    
    
    
      
    A note on p_auto_rest_auth
    
      
    The kit enables the schema with false. true is the more secure setting. Both were tested.
    
      
    Endpointfalsetrue
    
        
    POST t/item with token201201
    
        
    POST t/item without token401401
    
        
    metadata-catalog without token200 (open)401 (gated)
    
      
    
      
    The flag gates only the schema's Auto-REST surface. Hand-defined modules are controlled by the privilege you map, so the 403 doesn't depend on it.
    
      
    Caching: ORDS keeps an in-memory schema cache. After changing auto_rest_auth, the metadata-catalog only reflects it reliably once the cache refreshes or ORDS restarts.
    
    
    
  
    

    


    
  
    5. What the real database was missing
    
  
    The HTP result is real: revoking it does cause this 403. It just isn't what happened in the real database. Two facts ruled it out, and the code ORDS runs around a handler showed what was missing instead.
    
  
    
    
    
      
    Why HTP was ruled out
    
      
      
        
    • The failing schema could reach HTP, HTF, OWA, OWA_UTIL and WPG_DOCLOAD through PUBLIC.
      • 
        
    • Even a one-line handler, begin :status_code := 200; end;, got 403. So the cause wasn't anything a handler called.
      • 
      
    
      
    What was missing
    
      
    EXECUTE on SYS.DBMS_LOB and SYS.DBMS_PICKLER. Hardening had revoked both from PUBLIC, and the schema had no grant of its own.
    
      
    How the lab confirmed it
    
      
      
        
    • Revoking both from PUBLIC: every PL/SQL handler got 403 with the exact message, and GETs stayed 200.
      • 
        
    • Granting WS only DBMS_PICKLER: still 403, now on DBMS_LOB.
      • 
        
    • Granting WS both: everything worked.
      • 
      
    
    
    
    
    
      
    The fix
    
      
    Run by a DBA. Both are direct grants to one schema, so PUBLIC stays revoked.
    
      
    -- first: needed on every PL/SQL request
grant execute on sys.dbms_lob to <gateway_schema>;

-- then, only if ORDS's log still says
-- PLS-00201: identifier 'SYS.DBMS_PICKLER' must be declared
grant execute on sys.dbms_pickler to <gateway_schema>;
    
      
    Why the second grant waits: ORDS 25.3 asks DBMS_PICKLER on databases from 12c on, but whether ORDS 23 or 24 does hasn't been checked. And a missing DBMS_PICKLER can look fine for a while, because connections remember its answer (section 6).
    
      
    Which package is it? The 403 message never says. ORDS's log does, in a line like PLS-00201: identifier 'SYS.DBMS_LOB' must be declared. Checks that need no DBA, and the risk of each grant, are on ORDS 403, Hardened Grants.

    6. New vs warm connections
    
  
    Why DBMS_PICKLER is only asked now and then, and why that still doesn't make it optional. This is ORDS 25.3 on a 12c-or-newer database, where ORDS's code was read and the lab ran the tests. On older databases, ORDS 25.3 passes the headers another way and never asks.
    
  
    
    
    1
    ORDS keeps connections open
    Logging in for every request would be slow. So ORDS logs in a few times as ORDS_PUBLIC_USER and keeps those connections open: the pool. Each request borrows one, uses it as your schema, and hands it back.
    
    
    →
    
    
    2
    The first PL/SQL request asks
    Before your handler, ORDS hands the request headers to owa.init_cgi_env as OWA.VC_ARR arrays. To build one, the JDBC driver needs that type's layout, so it calls sys.dbms_pickler.get_type_shape, running as your schema.
    
    
    →
    
    
    3
    The connection remembers
    The driver keeps the answer in ORDS's memory, on that connection, for your schema. The next request on that connection skips the question. The connection is now warm.
    
  
    
  
    Analogy: each connection is a phone line with a notepad beside it. The first time a line handles your schema's PL/SQL request, the operator phones the records office (DBMS_PICKLER) to ask how the header form (OWA.VC_ARR) is laid out, and writes the answer on the notepad. After that, the operator just reads the notepad. If your schema isn't allowed to phone the records office, a line with an empty notepad can't serve you. A line that already has the answer still can, until that line is replaced.
    
  
    
    
    
      
    New connection NEW
    
      
    Just opened, just replaced, or never used for your schema. Its notepad is empty.
    
      
    request ─► line (new, empty notepad)
    │
    ▼
driver: "what does OWA.VC_ARR look like?"
    │asks sys.dbms_pickler.get_type_shape
    │as your schema
    ▼
  grant ✓ ─► write it down ─► run handler
  grant ✕ ─► PLS-00201 ─► 403
    
      
    Needs the grant, because the lookup runs as your schema.
    
    
    
    
    
      
    Warm connection WARM
    
      
    Already asked once, successfully, for your schema. Its notepad has the answer.
    
      
    request ─► line (warm, notepad filled)
    │
    ▼
driver reads the notepad
    │no call to DBMS_PICKLER,
    │so the grant is never checked
    ▼
init_cgi_env ─► handler ─► DBMS_LOB ─► 201
    
      
    Doesn't check the grant, because it never asks.

    The grant and the notepad are different things
    
      
    
        
    The grantThe notepad
    
        
          
    What it isEXECUTE on SYS.DBMS_PICKLER, for your schema or for PUBLICThe layout of OWA.VC_ARR, kept by the JDBC driver
    
          
    Where it livesIn the databaseIn ORDS's memory, on one connection, for one schema
    
          
    What it decidesWhether a lookup succeedsWhether a lookup happens at all
    
          
    How long it lastsUntil a DBA changes itUntil ORDS replaces the connection, moves it to another schema, or restarts
    
        
    
      
    So "new" and "warm" aren't a schema setting or a database setting. Nothing about them is stored in the database.
    
    
    
    
    
      
    What makes a connection new again
    
      
      
        
    • ORDS starts or restarts: every connection at once.
      • 
        
    • A busy moment: the pool opens extra connections, up to 10.
      • 
        
    • Age: a connection over 60 seconds old is closed right after its next request, and a new one takes its place. An idle one keeps its notepad until then; in the lab, idle connections still had it after 40 minutes.
      • 
        
    • Use: the same happens after 1,000 requests.
      • 
        
    • Another schema: when a connection switches to a different schema, the driver drops what it remembered. This comes from reading the driver's code. The lab had only one REST schema, so it wasn't tested.
      • 
      
    
      
    These are ORDS 25.3's defaults: jdbc.MaxLimit 10, jdbc.MaxConnectionReuseTime 60 seconds, jdbc.MaxConnectionReuseCount 1,000. Other versions and configurations may differ.
    
    
    
  
    
  
    What this means for you
    
      
      
    • "Not on every request" doesn't mean optional. Every new connection asks, and with regular traffic connections are replaced about once a minute.
      • 
      
    • Warm connections only hide a grant that was removed while ORDS was running, and only briefly. In the lab, 38 of 40 PL/SQL calls on warm connections still worked and 2 on new ones got 403. After a restart, every one failed.
      • 
      
    • They never help a new schema. A connection only becomes warm after a lookup that worked, and that needs the grant.
      • 
      
    • So a schema that works for days without DBMS_PICKLER has another reason. Its ORDS version may not ask, it may reach DBMS_PICKLER through a role or a direct grant, or its handlers aren't PL/SQL. Section 4, "Check your database", on ORDS 403, Hardened Grants tells you which.
      • 
      
    • DBMS_LOB has no notepad. The code after your handler calls it on every PL/SQL request, so a missing DBMS_LOB fails every time.
      • 
    
    
  
    

    


    
  
    7. Rebuild it on another computer
    
  
    The path that worked: an Oracle Database Free container plus ORDS in standalone mode, with no Tomcat. Commands use podman, and docker works the same. Every password shown is a throwaway test value, so use your own.
    
  
    
    
    Before you start
    
    
    Podman or Docker with about 8 GB of free disk and 4 GB of RAM, JDK 17 or newer, SQLcl (the sql command) or SQL Developer, and ORDS 25.x unzipped so you have bin/ords.
