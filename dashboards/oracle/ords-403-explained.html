ORDS 403, Explained

A REST gateway schema with only CREATE SESSION and CREATE SYNONYM got HTTP 403 on its plsql/block POST handlers, while json/collection GETs worked with the same token. This page rebuilds the investigation so you can run every request yourself.

Does the gateway need CREATE PROCEDURE?No
Real cause of the 403EXECUTE on SYS.HTP revoked from PUBLIC
The fixgrant execute on sys.htp to <gateway>
Key idea: ORDS wraps every plsql/block handler in code that uses SYS.HTP to build the HTTP response. If the schema can't reach HTP, the request fails before your code runs. GETs from a json/collection source never use HTP, so they keep working.

1. The setup at a glance

Two layers: the path a request travels, and the chain of schemas inside the database that does the work. The gateway never touches the repository directly. A definer's-rights package in the middle does. Tap any part.

Analogy: the gateway is a receptionist who may only pass notes to one office. The office (a definer's-rights package) has its own keys to the archive. And every written reply has to go through the building's printer, HTP. Take away the receptionist's printer access and every written reply fails, even though nothing else changed.

    4. What it proved
    
  
    
    
    
      
    Three suspects, one culprit
    
      
    HypothesisVerdictEvidence
    
        
    The gateway needs CREATE PROCEDURENoPhase 1 POST handlers returned 201 with only CREATE SESSION and CREATE SYNONYM
    
        
    The OAuth or privilege setup is the causeNoPhase 2: 401 without a token, 201 with a valid one
    
        
    Database hardening on SYS.HTPYesRevoking it from PUBLIC reproduced the 403 on POST, while GET stayed 200
    
      
    
      
    Why GET and POST differ: json/collection GETs go through ORDS's own SQL path and never touch HTP. Every plsql/block handler runs inside generated PL/SQL that needs HTP.
    
    
    
    
    
      
    A note on p_auto_rest_auth
    
      
    The kit enables the schema with false. true is the more secure setting. Both were tested.
    
      
    Endpointfalsetrue
    
        
    POST t/item with token201201
    
        
    POST t/item without token401401
    
        
    metadata-catalog without token200 (open)401 (gated)
    
      
    
      
    The flag gates only the schema's Auto-REST surface. Hand-defined modules are controlled by the privilege you map, so the SYS.HTP finding doesn't depend on it.
    
      
    Caching: ORDS keeps an in-memory schema cache. After changing auto_rest_auth, the metadata-catalog only reflects it reliably once the cache refreshes or ORDS restarts.
    
    
    
  
    

    


    
  
    5. Rebuild it on another computer
    
  
    The path that worked: an Oracle Database Free container plus ORDS in standalone mode, with no Tomcat. Commands use podman, and docker works the same. Every password shown is a throwaway test value, so use your own.
    
  
    
    
    Before you start
    
    
    Podman or Docker with about 8 GB of free disk and 4 GB of RAM, JDK 17 or newer, SQLcl (the sql command) or SQL Developer, and ORDS 25.x unzipped so you have bin/ords.
